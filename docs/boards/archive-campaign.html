The realm as it stands

How it works today

Norcoach is a small kingdom. Every set lifted, every message, every meal and every check-in is a scroll. The scrolls live in the Royal Archive (the Postgres database). But nobody reads from the Archive while the kingdom is awake.

Instead, at dawn (when the server starts) one Scribe walks into the Archive, reads every scroll ever written, and memorises them all. All day, every screen in the app asks the Scribe. When something changes, the Scribe updates his memory and sends a courier to the Archive with the scrolls that changed.

The Keep

The one server the app runs on, in the Netherlands.

Railway · 1 replica · /data volume

The Scribe

Holds every scroll in his head. Fast, but his head has a limit, and he is the only one.

getData() · the in-memory store · 768 MB heap

The Royal Archive

Where the scrolls truly live. Only read once, at dawn.

Railway Postgres · 52 mirror tables + kv

The couriers

Carry changed scrolls to the Archive after each change. They leave without waiting for a reply.

persist() · fire-and-forget · one transaction per save

With 11 clients this is quick and cheap. As coaches sign up, the kingdom grows, and four threats appear on the border:

The Scribe's head fills up

He has room for roughly 25–35 client-years of full use (an estimate). After that the Keep falls over.

He gets slower with every scroll

To know what changed, he re-reads his whole memory on every save, and a few chores re-read every client on every page view.

Lost couriers

A courier who trips is not sent again until some other change happens. A restart (every deploy) can cut a courier off mid-road. One strange letter on a scroll can block every courier after it.

Only one Keep

Two Scribes would number new scrolls the same way and overwrite each other. So the kingdom cannot add a second server when it gets busy.

Boring details

Boot: instrumentation.ts awaits initStore(); runtime.ts runs drizzle migrations, then loadStore() does one SELECT * per collection (52 tables) plus kv, builds the store, primes the writer with a full snapshot. Postgres is never read again for collection tables.

Save: persist() is fire-and-forget (only the workout outbox uses persistNow()). PgStoreWriter.save() stringifies every row of every collection, diffs against the last committed snapshot, and writes changed rows as multi-row upserts and deletes in one transaction. A failed save rolls back and is not retried until the next persist. On SIGTERM nothing waits for the writer.

Ids: allocId increments _seq in memory; ids are plain integer PKs, not sequences. Two processes would allocate the same ids and the upsert would silently overwrite. The /data volume is what stops Railway overlapping deploys.

Schema: mirror tables with every column nullable, dates as TEXT, an extra jsonb catch-all, no FKs, no secondary indexes. Only push_subscriptions and password_resets are read directly (pg/direct.ts).

Boot hazard: if kv _seq is missing, the app imports /data/ironline.json, which has not been written since the Postgres switch.

The campaign

Nine missions, in order

Each mission ships on its own, is rehearsed on the Training Grounds (staging) first, gets a copy in the vault before it goes live (a Railway snapshot and a git restore point), and has a retreat route if it goes wrong. A turn is one working session.

Age of Timber · secure the walls
1

Raise the Palisade

Nothing moves. We just stop losing couriers.

2–3 turnsRisk: lowClients notice: nothing
  • A courier who trips is sent again until he arrives, and a horn sounds if several trip in a row.
  • When the Keep is about to restart, the Scribe sends every courier first, and writes anything unsent onto an emergency scroll.
  • At dawn, the Scribe refuses to start from an empty or half-burnt Archive instead of reading months-old scrolls.
  • One strange letter can no longer block every courier after it.
  • A full copy of the Archive goes to the vault every night, and we practise restoring it once.
UnlocksNo lost saves on deploys or hiccups, and a real nightly backup.
Boring details
  • Backoff timer re-running writer.save() while the last save failed; consecutive-failure counter and last good save on /api/timing; distinct Sentry alert after N failures.
  • Shutdown: on SIGTERM start writer.save() at once, end the SSE chat streams through chatBus so server.close can finish, save again before draining ends; if the last save fails write /data/unsaved-<ts>.json and alert. Railway draining ≥ 15 s. Staging test with a chat screen open.
  • Boot guards: refuse to start when _seq is missing but tables hold rows; refuse the JSON import in production unless ALLOW_JSON_IMPORT=1; raise each _seq[table] to ≥ MAX(id).
  • Poison guard in store.ts fits(): int32 range, NUL stripped, rows without a numeric id skipped and reported.
  • Refuse kv keys named like any table, past or present (a stray key would replace the table on the next boot).
  • Nightly pg_dump to the backup bucket (postgresql client in the image); one restore rehearsed on staging.
  • Rollback: revert the commit. No schema or data change.
2

Pave the Roads

The Scribe stops re-reading the whole library for small questions.

2–3 turnsRisk: lowClients notice: faster pages
  • Client reminders stop running inside every page view and move to a clock.
  • The weight-progression chore only looks at workouts that changed, plus one full sweep at night.
  • The Feed, the chat list and the "needs you" counts are worked out in one pass per coach.
  • Saves only compare the shelves that actually changed.
UnlocksThe app stays quick as coaches arrive, before any data moves.
Boring details
  • applyDueClientReminders out of layout.tsx render into an instrumentation interval.
  • applyDueProgramDeployments: dirty assignment ids marked on every set write, edit and delete, plus a nightly full pass (a "last id" watermark would miss edits and deletes).
  • getActivityFeed filtered to the coach's clients first; listCoachAccounts cached per request; loadChatDock and coachNeeds grouped in one pass.
  • Dirty-collection tracking so snapshotOf only stringifies what changed.
  • Push keys and reset tokens stay out of the coach export (security).
  • Verify: /api/timing before and after on staging; Feed, rail and Home output identical for 3 coaches.
Age of Stone · build the outposts
3

Build the Training Grounds

A walled practice field with a copy of the kingdom, where nothing we do can touch real clients.

1–2 turns + a night windowRisk: mediumClients notice: one short night stop, maybe
  • A staging copy with its own storage and test keys: no real pushes, emails, invoices or photo deletions can leak out.
  • Check where the Archive stands. If it is far from the Keep (outside Europe), move it next door in one night window.
UnlocksEvery later mission can be rehearsed safely first.
Boring details
  • Staging restored from a prod dump with its own UPLOADS and BACKUP buckets, test-mode Stripe and Clerk, no push or mail keys, RECURRING_INVOICES=off, meeting reminders off, TZ=Europe/Amsterdam, SKIP_SEED=1, restricted access (health data and photos).
  • Relocation if needed: stop the app, pg_dump including the drizzle schema, restore, compare row counts and per-table md5, switch DATABASE_URL, start. The old database is a frozen backup; a rollback is a fresh dump back, not a pointer switch.
4

Forge the Seals

Groundwork, so scrolls can be written straight into the Archive later.

2–3 turnsRisk: mediumClients notice: nothing
  • The Archive numbers new scrolls itself, so two writers can never pick the same number.
  • The "don't send this twice" stamps live in the Archive, sealed together with the scroll they protect.
  • Times are written one clear way (today chat and set times use two formats).
  • While scrolls move, a deleted photo or video goes to a 30-day trash pit, never straight into the fire.
UnlocksSafe direct writes, with no duplicates and no lost media.
Boring details
  • Postgres sequences for moving tables and their parents, setval(MAX(id)) at every boot.
  • once_keys into a real table, written in the same transaction as its row; empty nonce stored as NULL.
  • Real timestamptz columns backfilled with stampMs' rule (Europe/Amsterdam).
  • Every promotion out of extra backfills in SQL and is verified by counting rows still holding the field in extra; re-run on every roll-forward.
  • Media deletions to a trash prefix for 30 days; a failed reference check means keep.
Age of Iron · move the stores
5

The Messenger Tower

Chat is the first store to move into the Archive. It becomes the model for all the rest.

6–9 turnsRisk: mediumClients notice: one short night restart
  • One gatekeeper owns all chat scrolls; every screen goes through him.
  • A week of shadow scouting: the new road runs silently beside the old one and every difference is written down. We only switch when the week is clean.
  • Switch at night. If anything is off, retreat to the previous version: the scrolls never left the Archive.
UnlocksThe fastest-growing store leaves the Scribe's head, and we have a tested recipe.
Boring details
  • 4A: chatStore module owns data.chat_messages (still in memory); every read and write site re-pointed (incl. editChatMessage, setChatMessageLink).
  • 4B: entry points fetch chat rows first, then compute synchronously; writes gain an await; mutations as single SQL statements (ON CONFLICT, jsonb_set) so concurrent reactions never lose one.
  • 4C: shadow reads compared against the committed snapshot (writer.last), JSON canonicalised, sampled, with per-code-path counts; new write paths exercised on staging against a separate table. Exit: 7 clean days.
  • 4D: night cut-over; table leaves COLLECTIONS, Data and emptyData with an explicit exclude list; ids kept (chat-${id} keys); nonce via ON CONFLICT on the new column; order by the real timestamp, then id. Rollback: previous build reloads the table at boot.
6

Clear the Health Caravans

Apple Health workouts are one giant scroll rewritten on every sync. Split it into proper rows.

2 turnsRisk: low
Boring details

health_workouts is one kv value holding every client's newest 400 workouts; any sync rewrites it whole and every save re-stringifies all of kv. Move it to a table early; compare element counts against the blob; keep the blob until the shadow period ends.

The Herald's Hall

Notifications and the activity log move next.

5 turnsRisk: medium
Boring details

coach_activity: index (client_id, created_at), a unique dedupe key for reminders, the chat↔notification match by text and ±5 s replaced by a stored message id set at write time and backfilled. 24 logCoachActivity callers, some inside synchronous jobs (recurring invoices): expect about 1.5× the first guess.

8

The Granary and the Well

The food diary (with saved meals, saved days and meal photos, moved together), then check-in figures.

8–10 turnsRisk: medium
Boring details
  • food_entries + calorie_logs + food_days, with food_meals, saved_meals, meal_photos together so using a saved meal stays one transaction; indexes (client_id, date), unique (client_id, date) on calorie_logs; saved_meal_id promoted.
  • metric_entries: index (metric_definition_id, period), source promoted, a batch query for the reminder pass and healthSync's scans.
Age of Crowns · the last stronghold
9

Siege of the Iron Logs

Logged sets, with workouts and session days. The biggest and most tangled store, so it goes last.

12–18 turnsRisk: highClients notice: one short night restart
  • Every set learns which client it belongs to.
  • Two weeks of shadow scouting instead of one.
  • The workout outbox (offline saving in the gym) keeps working throughout.
UnlocksThe Scribe's head holds only small things. A second Keep becomes possible later.
Boring details
  • client_id on set_logs set at write time and backfilled, re-backfilled at cutover; gym_id and unit promoted; indexes (client_id, logged_at) and workout_assignment_id.
  • Unique (workout_assignment_id, set number): the same migration deletes twins first (newest by logged_at, id), inserts become ON CONFLICT DO UPDATE, so boot never fails and outbox replays update.
  • Parents in memory get await persistNow() before a direct child insert (or sequences first), so a crash can never hand a parent id to another client.
  • 63 references in 8 files; async spreads through workout_assignments (132) and program_days (127). Comparison scripts are their own work.
